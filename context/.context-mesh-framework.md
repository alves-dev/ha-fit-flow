# Context Mesh Framework

Context Mesh keeps durable project knowledge close to the code while separating product intent from implementation knowledge. It follows three steps:

1. **Intent** — describe what users need and why it matters.
2. **Build** — make technical decisions and implement the intent with reusable patterns.
3. **Learn** — record outcomes, discoveries, and changes so future work starts with current context.

## File type separation

- **Feature files** (`intent/feature-*.md`) describe only user/business behavior: What, Why, and functional acceptance criteria. They may link to decisions and patterns but must not contain technical implementation details.
- **Decision files** (`decisions/*.md`) record technical choices, architecture, libraries/frameworks, rationale, alternatives, and outcomes. They explain **HOW the project chose to work**.
- **Knowledge files** (`knowledge/patterns/*.md`, `knowledge/anti-patterns/*.md`) record reusable implementation guidance. Pattern files include code examples and explain **HOW TO IMPLEMENT**. Anti-patterns record approaches to avoid.
- **Agent files** (`agents/*.md`) contain role-specific execution guidance. The directory is intentionally empty until a specialized agent is needed.
- **Project intent** (`intent/project-intent.md`) summarizes the product purpose and current state without becoming a technical design document.
- **Evolution files** (`evolution/changelog.md`) record the documented state and later context changes.

## Plan, Approve, Execute

For non-trivial changes, agents must:

1. **Plan** — load context, state the intended behavior and affected files, and identify or create the relevant decision.
2. **Approve** — confirm the plan when the change introduces meaningful architecture, risk, or external impact.
3. **Execute** — implement, validate, and update feature/decision/pattern/changelog files as appropriate.

For small, reversible maintenance changes, approval may be implicit in the user request. Never silently introduce a materially different architecture.

## When to create files

Create a file when knowledge is durable, reusable, or important for future decisions. Update an existing file when the concept already has a home. Do not create speculative files for behavior that is not present in the codebase.

## Context structure

```text
context/
├── .context-mesh-framework.md
├── intent/              # What and Why
├── decisions/           # Technical choices and rationale
├── knowledge/
│   ├── patterns/        # Implementation examples
│   └── anti-patterns/   # Practices to avoid
├── agents/              # Specialized agent instructions
└── evolution/           # Changelog and learning history
```

## Definition of Done

- Intent is clear and separated from implementation.
- Relevant decisions exist before introducing a new technical approach.
- Code follows applicable patterns and avoids recorded anti-patterns.
- Tests and static checks pass.
- Bidirectional links are added where a feature, decision, and pattern relate.
- Status sections are present and accurate.
- The evolution changelog reflects the resulting state.

## Bidirectional links

Use relative Markdown links. Features link to applicable decisions and patterns; decisions link back to the features they support; patterns link to related decisions and features. Keep links specific and do not add unrelated cross-references.

## Status sections

Every intent, decision, and pattern file ends with a Status section containing Created date and Status. Existing-code decisions should be marked Accepted and note that they were documented from implementation. Outcomes may remain open when no historical outcome is recorded.
